# 개발사항정의서(WIP5 v0.3) 리뷰 — 웹팀 정의서 ↔ Labbit 앱 정합성

대상: 웹 구현팀의 `개발요구사항정의서` (FR-001~024, NFR·IFR·DR·CR, 추적표)
관점: 우리(안드로이드) 앱이 어디까지 맞춰져 있고, 무엇을 맞춰야 하는지.

> **업데이트(2026-10-28)**: 이후 금융인증서 로그인(챌린지-응답), 간편비밀번호 6자리(PBKDF2·5회잠금·기기바인딩·보안키패드),
> E2E 필드 암호화를 구현했습니다. 아래 3항목 중 **보안 키패드는 완료**, FR-001(인증서)·FR-018(계좌비번 암호화 전송)·
> FR-023(생체/간편인증)은 구조가 갖춰졌습니다. 상세 흐름은 `docs/security/SECURITY-LAB.md`·`docs/api/openapi.yaml(v1.2)` 참고.

## 1. 총평
- **정의서의 '기능요구사항_상세_API기준' 시트는 우리 `docs/api/openapi.yaml` 위에 작성됐습니다.**
  참조 엔드포인트(`/auth/challenge`, `/auth/login/certificate`, `/signup/identity-verifications`,
  `/accounts`, `/transfers/recipient-inquiry`, `/transfers/limits`, `/withdrawals/cardless`,
  `/cards/{cardId}/suspension`, `/security/status` 등)가 모두 우리 스펙과 일치합니다.
  → **두 팀이 같은 API 계약을 공유**하고 있어 정합성이 매우 높습니다. 이 스펙을 "단일 진실(source of truth)"로
  유지하는 것이 핵심입니다.
- 우리 앱은 FR 24개 중 **대부분을 이미 구현**했습니다(로그인·가입·조회·이체·출금·카드·계좌관리·보안상태 등).
- 정의서의 `FR-017~024`("추가 제안")는 우리가 이미 만든 계좌관리·계좌비번·한도해제·카드없는출금·카드신청·
  내카드관리·생체등록·보안상태와 1:1로 대응합니다. 우리 구현이 그들의 "제안"을 앞서 검증해 준 셈입니다.
- 주의: 우리 앱은 **보안 실습(취약/안전 토글)** 앱입니다. 정의서의 기준(NFR-003 등)은 우리의 **안전 모드**가
  대응합니다. 취약 모드는 교육용이며 정의서 기준이 아님을 양 팀이 공유해야 합니다.

## 3. 우리가 맞춰야 할 항목 (우선순위순)
1. **알림 설정 화면(FR-011)** — 스텁을 실제 토글 화면으로. `GET/PUT /users/me/notification-settings` 연동, 저장 실패 시 롤백.
2. **자동 로그아웃·세션(FR-002)** — 10분 유휴 자동 로그아웃, 1분 전 연장 팝업, 토큰 만료 시 1회 재발급 재시도. (서버가 없으니 재발급은 모킹으로 흐름만.)
3. ~~보안 키패드(FR-006·018)~~ — **구현 완료**(`SecureKeypad.kt`). 남은 건 계좌 비밀번호 변경 화면에 실제 연결.
4. **계좌 비밀번호 변경 실제 플로우(FR-018)** — 안내 메시지 → `PUT /accounts/{id}/password` 연동(암호화 PIN).
5. **거래내역 cursor 페이지네이션(FR-005)** — size≤100, nextCursor 종료 조건. 현재 전체 로드.
6. **고객센터/문의 분리(FR-013 vs 014)** — 정적 안내(연락처·운영시간·분실신고)와 1:1 문의를 화면상 분리.
7. **생체등록·해제 화면(FR-023)** — 마이페이지에서 실제 등록/해제 동작 연결.

## 4. 우리가 웹팀에 제안/공유할 것
- **문의(FR-014)·공지(FR-015)는 정의서에서 "API 미정의 보류"**이지만, 우리 `openapi.yaml v1.1`에 이미
  `/inquiries`, `/notices`, `/posts`, `/search`를 정의했습니다. 이걸 공유하면 웹팀의 보류 3건을 바로 풉니다.
- **FAQ(FR-016)**는 양쪽 다 없음 → 공통으로 `/faqs`(카테고리·키워드 검색) 신규 정의 제안.
- **FR-001 로그인 문구**: FR 목록은 'ID·비밀번호 및 인증서', 상세·API는 '인증서/생체'. 목록 문구를 상세에 맞춰
  정정하거나, ID/PW 로그인을 추가할지 결정 필요(정의서도 같은 지적을 남김).
- 단일 계약 유지: `openapi.yaml`을 두 팀 공용으로 두고 변경 시 동기화. 화면↔엔드포인트 매핑은
  `docs/api/README.md` 표를 그대로 추적표(RTM) 채우기에 재사용 가능.

## 5. 비기능·제약·기타 시트 지적
- **CR-001이 "구현 언어 C11, 대상 Linux x86_64"로 예시 그대로** 남아 있음 → 템플릿 잔재.
  실제 스택(웹: 해당 프레임워크 / 앱: Kotlin·Android minSdk26·targetSdk35)으로 교체 필요.
- **NFR-003(TLS 1.2+ 외부통신)** ↔ 우리 `network_security_config.xml`(cleartext 차단)와 정합. 단 보안 실습 취약 모드는 예외.
- **NFR-007(단위시험 커버리지 70%)** — 현재 우리 앱은 데모라 테스트 미작성. 목표치 적용 시 테스트 추가 필요.
- **IFR·DR·비기능·추적표 시트는 대부분 미작성(〈 〉 플레이스홀더)** → 값 채워야 승인 단계 진행 가능.
- 데이터요구사항(DR): 개인정보 보존·파기 기준이 비어 있음 → 우리 앱의 로컬 저장(암호화 저장소·백업 제외 규칙)과
  맞물리므로 함께 기준 정의 권장.

## 6. 결론
정합성은 이미 높습니다(공유 API 계약). 우리 쪽 보완은 대부분 **화면·동작 디테일**(알림설정·자동로그아웃·보안키패드·
페이지네이션)이고, 반대로 우리가 **문의·공지 API 정의를 제공해 웹팀 보류를 풀 수 있습니다.** FR-001 문구,
FAQ 신규 정의, CR-001 템플릿 잔재가 양 팀 공통 정리 포인트입니다.
